Punto Flotante · Implementación (ATS)

Nota Implementacional
✦ Implementación en: ATS (cambiar)
← Nota conceptual · Práctica →

La nota conceptual afirma que fl : ℝ → 𝔽 es una función que proyecta cada real a su representable más cercano, y que la aritmética de máquina es a ⊕ b = fl(a + b), no a + b. Aquí lo volvemos tangible. La vía de ATS exhibe algo que las “torres numéricas” de un lenguaje dinámico no pueden: un único binario, compilado a C y corriendo a velocidad nativa, en el que la aritmética exacta (racionales de GMP, que modelan ℝ) y la aritmética de máquina (el double IEEE 754, que es 𝔽) conviven y se imprimen una junto a la otra. El double nativo es 𝔽 — no una simulación de él. Todo lo que sigue es código real y la respuesta literal del programa.

El núcleo: dos aritméticas en un binario, a velocidad de C

ATS no tiene una “torre de exactos” incorporada como un Lisp. La construye de forma explícita: incrusta C dentro del programa y llama a GMP (la biblioteca de precisión arbitraria) para la aritmética exacta, mientras el double del propio ATS hace de 𝔽. Ese bloque entre %{^ y %} es C puro; la función exact_add_str suma dos números como racionales exactos y devuelve su expansión decimal completa.

%{^
#include <gmp.h>
/* aritmetica EXACTA con racionales de precision arbitraria (GMP) */
static void exact_add_str(double a, double b, char* out, int n) {
  mpq_t qa, qb, qs;
  mpq_inits(qa, qb, qs, NULL);
  mpq_set_d(qa, a);          /* el double a, leido SIN perdida como racional */
  mpq_set_d(qb, b);
  mpq_add(qs, qa, qb);       /* suma exacta en ℚ */
  mpf_t f; mpf_init2(f, 256);
  mpf_set_q(f, qs);
  gmp_snprintf(out, n, "%.40Fg", f);   /* 40 digitos: la verdad de ℝ */
  mpq_clears(qa, qb, qs, NULL);
}
%}
extern fn exact_add_str
  (a: double, b: double, out: ptr, n: int): void = "mac#exact_add_str"

La función caso corre las dos versiones lado a lado: a + b es el + de la máquina —es decir, fl(a+b), la suma de 𝔽— y exact_add_str es la suma en ℝ. Luego compara si fl absorbió o no el término pequeño.

fn caso (a: double, b: double): void = let
  val flotante = a + b                 (* esto ES fl(a+b): el + de la maquina *)
  var buf = @[char][128]()             (* buffer en pila, sin GC: estilo C *)
  val () = exact_add_str(a, b, addr@buf, 128)
  val exacto = $UNSAFE.cast{string}(addr@buf)
in
  println!("  exacto a+b   = ", exacto, "   (racional GMP, sin redondeo)");
  println!("  flotante a+b = ", flotante, "   (fl proyecta a F)");
  if a = flotante then
    println!("  >> fl ABSORBIO b por completo: el resultado es identico a 'a'.")
  else
    println!("  >> el termino pequeno si sobrevivio (a su escala).")
end
Lo que responde el programa

  a            = 100000000000000000000.000000
  b            = 1000.000000
  exacto a+b   = 100000000000000001000   (racional GMP, sin redondeo)
  flotante a+b = 1e+20   (fl proyecta a F)

  a            = 1.000000
  b            = 0.000010
  exacto a+b   = 1.000010000000000000000818030539140313095   (racional GMP, sin redondeo)
  flotante a+b = 1.0000100000000001   (fl proyecta a F)
  >> el termino pequeno si sobrevivio (a su escala).

  a            = 1.000000
  b            = 0.000000
  exacto a+b   = 1.000000000000000111022302462515654042363   (racional GMP, sin redondeo)
  flotante a+b = 1   (fl proyecta a F)
  >> fl ABSORBIO b por completo: el resultado es identico a 'a'.

El primer caso es la lección central. En ℝ, 10²⁰ + 10³ = 100000000000000001000 — el GMP, que no sabe redondear, retiene los veintiún dígitos. Pero en 𝔽 el espaciado entre representables a escala 10²⁰ es de unos ~16000, mucho mayor que el 1000 que intentamos sumar: fl no tiene dónde ponerlo y lo absorbe por completo. El resultado de máquina es idéntico a a. El programa lo verifica con if a = flotante y lo declara: fl ABSORBIO b por completo.

El segundo y tercer caso afinan la intuición. 1 + 10⁻⁵ sí sobrevive (el espaciado a escala 1 es ~10⁻¹⁶, mucho menor que 10⁻⁵). Y 1 + ½ε_mach —justo a la mitad del último escalón— vuelve a ser absorbido por el redondeo al par. La absorción no es “lo pequeño desaparece”: es “lo que cae bajo medio espaciado desaparece”.

ε_mach (espaciado) vs u (cota de redondeo): calculados, no recitados

La conceptual distingue dos cantidades que suelen confundirse: el espaciado relativo ε_mach = 2⁻⁵² y la unidad de redondeo u = ε_mach/2 = 2⁻⁵³. El código no las cita: las descubre, buscando el menor 2⁻ᵏ que aún cambia el 1.0.

fn demo_epsilon (): void = let
  (* buscamos el menor 2^-k tal que 1 + 2^-k aun se distingue de 1 *)
  fun loop (e: double): double =
    if d_add(1.0, d_div(e,2.0)) = 1.0 then e else loop(d_div(e,2.0))
  val eps = loop(1.0)
in
  println!("  eps_mach (espaciado a O(1)) = ", sci(eps));
  println!("  u = eps_mach/2 (cota redondeo) = ", sci(d_div(eps,2.0)));
  println!("  1.0 + u  distinguible de 1.0?  ", (d_add(1.0, d_div(eps,2.0)) <> 1.0));
  println!("  1.0 + eps distinguible de 1.0? ", (d_add(1.0, eps) <> 1.0))
end
Lo que responde el programa 
==== /u1/t1  espaciado eps_mach vs unidad de redondeo u ====
  eps_mach (espaciado a O(1)) = 2.2204460492503131e-16
  u = eps_mach/2 (cota redondeo) = 1.1102230246251565e-16
  1.0 + u  distinguible de 1.0?  false
  1.0 + eps distinguible de 1.0? true

El bucle loop divide e a la mitad hasta que 1.0 + e/2 deja de distinguirse de 1.0; el último e que sobrevivió es ε_mach. El resultado es exactamente 2.2204…e-16 = 2⁻⁵², el espaciado a escala O(1). La unidad de redondeo es su mitad. Y las dos últimas líneas hacen tangible la diferencia: 1.0 + u no se distingue de 1.0 (cae justo en la frontera y el redondeo al par lo absorbe), pero 1.0 + ε_mach sí. La distinción del texto, comprobada en ejecución.

El compilador como “estudiante obtuso pero insistente”

Aquí aparece lo que distingue a ATS de cualquier vía de lenguaje dinámico, y conviene anticiparlo porque domina la nota siguiente (u1t2). En Racket, el intérprete te corrige en ejecución: corres el programa y ves el dígito perdido. En ATS hay un corrector aún más obtuso e insistente que actúa antes de ejecutar: el verificador de tipos.

El código de la Unidad 1 distingue dos cantidades con dos nombres y dos fórmulas separadas (eps_mach = 2⁻⁵² y u = 2⁻⁵³). Esa separación no es decorativa: en las notas siguientes, los exponentes de las cantidades físicas viajan dentro del tipo, y el compilador —que hace exactamente lo escrito, sin intuición ni indulgencia— rechaza cualquier confusión entre ellas como un error de compilación. El double que aquí corre a velocidad de C es, en u1t2, una cantidad con dimensiones verificadas. Misma máquina, dos niveles de obstinación: el runtime te corrige el número; el compilador te corrige el significado del número.

Por qué la vía de ATS

Tres rasgos que esta nota deja ver y que las demás vías no comparten:

  • Un solo binario, dos aritméticas. No hay “modo exacto” del lenguaje: la aritmética exacta es C

    • GMP incrustado, y la de máquina es el double nativo. Ambas compilan al mismo ejecutable y corren a velocidad de C. La comparación ℝ↔︎𝔽 no paga overhead de interpretación.

  • fl no se modela: se ejecuta. El + de la línea val flotante = a + b es fl(a+b), literalmente la instrucción de punto flotante del procesador. No simulamos el redondeo; lo observamos.

  • El control de bajo nivel es explícito y seguro. El buffer @[char][128]() vive en la pila, sin recolector de basura, como en C — pero el sistema de tipos de ATS vigila su uso. Es el “C con garantías” que hace de ATS la vía de quien necesita velocidad y corrección.

Ejecuta tú

patscc -DATS_MEMALLOC_LIBC -o fiscomp_u1 fiscomp_u1.dats -lgmp -lm
./fiscomp_u1

Requiere ATS2 (ats2-lang) y libgmp-dev. El flag -lgmp enlaza la aritmética exacta; -lm, las funciones matemáticas; -DATS_MEMALLOC_LIBC usa el malloc de C para las closures. El programa completo incluye además los bloques de u1t2–u1t5 (dimensiones como tipos, cancelación catastrófica, número de condición, regla de oro). Córrelo, cambia los números de caso(...), intenta predecir antes de pulsar enter si fl absorberá el término pequeño — y deja que el programa te corrija. Cuando lo hayas hecho, pasa a la práctica.
