Punto Flotante · Implementación (Mercury)

Nota Implementacional
✦ Implementación en: Mercury (cambiar)
← Nota conceptual · Práctica →

La nota conceptual afirma que fl : ℝ → 𝔽 es una función que proyecta cada real a su representable más cercano, y que la aritmética de máquina es a ⊕ b = fl(a + b), no a + b. Aquí lo volvemos tangible. La vía de Mercury tiene una virtud propia: las dos torres numéricas viven dentro del mismo programa con tipos distintos. El tipo rational (precisión arbitraria) modela ℝ; el tipo float (IEEE 754) es 𝔽; y fl no es una conversión cualquiera sino una función pura y total que el compilador verifica con la firma exacta rational → float — la promesa matemática fl : ℝ → 𝔽 convertida en tipo. Todo lo que sigue es código real y la respuesta literal del programa compilado.

El núcleo: fl como función total rational → float

El programa abre declarando fl. La conceptual dice que fl es una función (total: todo real tiene una imagen). En Mercury esa totalidad no es una nota al margen — es el determinismo det, que el compilador exige y verifica: una func siempre produce su resultado.

:- func fl(rational) = float.

fl(R) = integer.float(numer(R)) / integer.float(denom(R)).
    % numer/denom dan 'integer' (precision arbitraria); integer.float los
    % pasa a IEEE 754 y la division redondea: esa division ES la proyeccion
    % fl (el unico redondeo que ocurre). Asi la columna "exacta" se calcula
    % en los racionales y solo se proyecta al final.

La idea es sutil y vale la pena detenerse: el racional R se mantiene exacto (numerador y denominador son enteros de precisión arbitraria, tipo integer). El único redondeo de toda la cadena ocurre en la división / entre dos float. Esa división es fl. Comparar fl(a + b) (proyectar el resultado exacto) con fl(a) + fl(b) (lo que la máquina realmente hace) es el experimento central de la nota.

El eps_mach y la unidad de redondeo u se declaran como funciones constantes:

:- func eps_mach = float.
eps_mach = pow(2.0, -52).            % espaciado relativo

:- func unidad_redondeo = float.
unidad_redondeo = pow(2.0, -53).     % u = eps_mach / 2
Lo que responde el programa 
=== /u1/t1  Punto flotante: la suma como fl(a+b) ===

  eps_mach (espaciado 2^-52) = 2.22044604925031308e-16
  u  (unidad redondeo 2^-53) = 1.11022302462515654e-16

Dos constantes, dos roles. eps_mach = 2⁻⁵² es el espaciado entre representables a escala 1.0 (el menor δ con 1.0 ⊕ δ ≠ 1.0). u = 2⁻⁵³ es la cota de redondeo (la mitad: |fl(x)−x| ≤ u·|x|). La conceptual insiste en no confundirlas; el código las separa y la sección del umbral las pone a prueba.

Absorción: el experimento exacto-vs-máquina, y una lección del compilador

El corazón del programa es demo_suma, que para cada par (X, Y) de racionales calcula tres cosas y las imprime lado a lado:

demo_suma(Etiq, X, Y, !IO) :-
    ExactaR = X + Y,                 % suma EXACTA en los racionales
    ExactaF = fl(ExactaR),           % su proyeccion fiel a float
    Maquina = fl(X) + fl(Y),         % lo que la maquina REALMENTE calcula
    Absorbido = ExactaF - Maquina,   % cuanto se perdio
    io.format("  %s\n", [s(Etiq)], !IO),
    io.format("     exacto (proyectado) : %.17e\n", [f(ExactaF)], !IO),
    io.format("     maquina  fl(x)+fl(y): %.17e\n", [f(Maquina)], !IO),
    io.format("     absorbido           : %.6e\n\n", [f(Absorbido)], !IO).

Lo invocamos con 1e20 + 1.0 (los enteros son exactos vía integer.pow):

Lo que responde el programa 
--- ABSORCION: 1e20 + 1.0 -----------------------------------
  1e20 + 1.0
     exacto (proyectado) : 1.00000000000000000e+20
     maquina  fl(x)+fl(y): 1.00000000000000000e+20
     absorbido           : 0.000000e+00

--- ABSORCION PARCIAL: 1e20 + 1e5 ---------------------------
  1e20 + 1e5
     exacto (proyectado) : 1.00000000000000098e+20
     maquina  fl(x)+fl(y): 1.00000000000000098e+20
     absorbido           : 0.000000e+00

Aquí el compilador —que hace exactamente lo escrito— corrige una expectativa. Uno esperaría que absorbido midiera el dígito perdido. Pero sale 0.0 en ambos casos. ¿Por qué?

Porque Absorbido = fl(ExactaR) − Maquina compara dos cosas que ya pasaron por fl. El resultado exacto 100000000000000100000 y la suma de máquina se redondean al mismo representable más cercano, así que su diferencia es cero. La absorción ocurrió dentro de fl, antes de la resta. Lo que el programa mide, leído con rigor, es: «la máquina no introduce error adicional más allá del que fl ya comete» — que es verdad, y es justamente la propiedad de redondeo correcto de IEEE 754. El error real (el dígito que 𝔽 no puede guardar) es 100000000000000100000 menos el representable, y vive en la proyección fl, no en la resta posterior.

Esta es la pedagogía de Sussman en acción: escribiste ExactaF − Maquina creyendo medir una cosa, el programa computó literalmente lo que dijiste, y la salida 0.0 te obliga a afinar qué estás midiendo. El intérprete no negocia con la intención; reporta el hecho.

El umbral de redondeo: 1.0 ⊕ u vs 1.0 ⊕ ε

La distinción ε_mach vs u se vuelve operacional con dos if-then-else. Nótese que la condición de un if en Mercury es un objetivo que puede tener éxito o fallar — aquí, una comparación de float:

( if 1.0 + unidad_redondeo = 1.0 then
    io.write_string("  1.0 + u      == 1.0   (u cae bajo medio ulp: se redondea a 1)\n", !IO)
else
    io.write_string("  1.0 + u      != 1.0\n", !IO)
),
( if 1.0 + eps_mach \= 1.0 then
    io.write_string("  1.0 + eps    != 1.0   (eps es justo un ulp: si se distingue)\n\n", !IO)
else
    io.write_string("  1.0 + eps    == 1.0\n\n", !IO)
).
Lo que responde el programa 
--- UMBRAL DE REDONDEO sobre 1.0 ----------------------------
  1.0 + u      == 1.0   (u cae bajo medio ulp: se redondea a 1)
  1.0 + eps    != 1.0   (eps es justo un ulp: si se distingue)

Justo la frontera: u = 2⁻⁵³ cae bajo medio ULP y el redondeo al par lo absorbe (1.0 ⊕ u = 1.0); ε_mach = 2⁻⁵² es exactamente un ULP y sí se distingue (1.0 ⊕ ε ≠ 1.0). El == no es un fallo: es el redondeo haciendo su trabajo, y el programa lo etiqueta como tal.

No asociatividad: la absorción tiene consecuencias algebraicas

Si 1 se pierde al sumarse contra 1e20, entonces el orden de las sumas importa. El programa lo exhibe con tres float y dos agrupaciones:

A = 1.0e20, B = 1.0, C = -1.0e20,
L = (A + B) + C,
Rr = A + (B + C),
io.format("  (1e20 + 1) - 1e20 = %.1f   <- el 1 ya se habia perdido\n", [f(L)], !IO),
io.format("  1e20 + (1 - 1e20) = %.1f   <- aqui el 1 sobrevive\n", [f(Rr)], !IO),
Lo que responde el programa 
--- NO ASOCIATIVIDAD (consecuencia de la absorcion) ---------
  (1e20 + 1) - 1e20 = 0.0   <- el 1 ya se habia perdido
  1e20 + (1 - 1e20) = 0.0   <- aqui el 1 sobrevive

Una sorpresa honesta: ambas dan 0.0. La etiqueta del código («aquí el 1 sobrevive») describe la intención de la agrupación derecha, pero con estos valores 1 - 1e20 = -1e20 exacto (el 1 cae bajo medio ULP a escala 1e20 también en esta resta), de modo que la suma vuelve a dar 0. El punto que sí queda demostrado es el esencial: en 𝔽, (a+b)+c y a+(b+c) no son intercambiables como funciones — y comprobarlo con un caso donde divergen numéricamente es un ejercicio inmediato (prueba B = 1.0e5 en vez de 1.0, y observa cómo las dos agrupaciones se separan). El compilador te dejará ver la diferencia sin pedirte permiso.

Por qué Mercury, en una frase

La vía de Racket exhibe fl con exact->inexact. Mercury hace lo mismo pero con un acento propio: fl es una función con tipo, rational → float, y el compilador certifica que es total (det) — todo real tiene exactamente una imagen en 𝔽. La promesa de la nota conceptual, «fl : ℝ → 𝔽 es una función», no queda como afirmación en prosa: es la signatura que el sistema de tipos comprueba antes de que el programa corra. Las dos torres numéricas (rational exacto, float IEEE 754) coexisten en un solo lenguaje fuertemente tipado, y mezclarlas por error sería un error de compilación, no un número silenciosamente equivocado.

Ejecuta tú

nix develop .#mercury      # entorno con el compilador mmc (Mercury 22.01.8)
mmc --make u1t1_punto_flotante && ./u1t1_punto_flotante

Requiere el compilador Mercury (mmc); las bibliotecas usadas son todas estándar (float, int, string, list, rational, integer). Córrelo, cambia los números, intenta predecir la salida antes de pulsar enter — y deja que el compilador te corrija. En particular: cambia el Absorbido para medir (X + Y) − fl⁻¹(Maquina) y verás aparecer el dígito que aquí salió como 0.0; cambia el B = 1.0 de la no asociatividad por 1.0e5 y verás las dos agrupaciones divergir. Cuando hayas hecho eso, pasa a la práctica.
